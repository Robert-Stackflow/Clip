# 截图与录制-独立应用拆分方案

日期：2026-10-08。状态：产品方向已明确；本文记录边界与迁移方案，代码尚未完成拆分。

用户已选择：**独立应用，迁移整套截图与录制功能。** 新应用名称暂未确定。目标需求见[截图与录制-需求文档](D:/Repositories/Clip/docs/development/截图与录制-需求文档.md)。

## 1. 产品边界

| 产品 | 功能归属 |
| --- | --- |
| Clip | 剪贴板捕获、历史、搜索、分类、收藏、堆栈、拖拽容器、快捷回复、快捷面板，以及记录预览、复制、粘贴和保存 |
| 独立截图与录制应用 | 截图选区、元素检测、标注、图片编辑、长截图、贴图、录屏、录音、摄像头、GIF、OCR、翻译、表格与 LaTeX 识别，以及自身的设置和导出任务 |

本次独立方向覆盖需求文档中的全部 U 类功能。尚未实现的长截图、GIF 和识别等能力直接在新应用中建设，不先扩展 Clip 再迁移。

Clip 的图片预览、复制、粘贴、保存以及既有格式读取仍是剪贴板工作的一部分。用户已补充确认现有图片编辑也可整体迁移，并通过 URI 等方式互通；Clip 保留主动调用独立编辑器的入口，复杂标注编辑和置顶贴图归新应用。

Clip 已有图床、AI 和其他工具能力，本次没有要求迁移这些模块；新应用所需的识别、翻译或上传配置独立设计，不读取 Clip 的服务令牌或整套设置。

## 2. 产品独立性

1. 独立程序入口、应用标识、安装器、版本及更新机制。
2. 独立进程、托盘、退出和开机启动设置。
3. 独立设置、用户目录、素材工程、恢复草稿及任务队列。
4. 未安装或未运行 Clip 时，仍能完成所有核心捕获和输出流程。
5. Clip 退出、锁定历史、迁移目录或升级时，不中断新应用的录制。
6. 新应用退出或升级时，不影响 Clip 的剪贴板工作。
7. 每款应用只包含所需运行资源；代码复用不导致安装包必须携带另一款完整程序。
8. 用户分别选择是否自启动，不互相拉起并长期常驻。

源码初期可复用已有模块，目标工程应能单独构建和发布。是否采用完全独立仓库或同仓双应用可在落地时决定；默认建议独立仓库，避免新应用持续依赖 Clip 主工程的构建与版本。

## 3. 两款应用如何协作

### 3.1 第一阶段：系统剪贴板与普通文件

- 新应用主动复制截图后，Clip 按已有剪贴板规则记录图片。
- 新应用复制文字、公式或表格结果后，Clip 按适用格式捕获。
- 用户主动复制或导出视频、音频、GIF 文件后，Clip 可记录适用的文件引用。
- 新应用停止录制不自动把整段录制塞入 Clip 数据库；由用户选择保存、复制或其他输出动作。
- Clip 的排除应用、暂停记录和历史锁定规则仍有效；不能为了联动绕过这些设置。

这条协作路径不需要共用数据库，也不需要两款应用都运行。

### 3.2 已纳入方向：URI 调用独立图片编辑器

用户提出将现有图片编辑一起迁移，并通过 URI 等方式互通。Clip 图片详情保留“编辑图片”操作，实际编辑在独立应用中完成；“用独立工具贴图”可复用交接机制，仍作为扩展建议。

建议流程：

1. 用户在 Clip 中选择图片并点击编辑。
2. Clip 准备这一张图片的素材副本和有期限的交接请求；历史数据库和密钥不参与交付。
3. Clip 通过 URI 唤起新应用；已运行时将请求交给既有实例，不重复启动主进程。
4. 新应用校验并消费交接请求，建立独立编辑会话；支持多个请求并清楚区分素材。
5. 用户完成后选择复制、另存或回传。Clip 退出不影响编辑器继续编辑和另存。
6. 回传时 Clip 校验对应请求与结果，默认保存为新图片记录，保留原图；取消或放弃不生成新记录。
7. 交接副本、结果和凭据按会话状态及保留期限清理；失败时仍保留独立应用可另存的结果。

如果以后支持更新原记录，需要单独定义用户动作、原内容版本校验和冲突处理，不将覆盖作为默认行为。

### 3.3 URI 与素材传输的职责

URI 只表达动作、协议版本和一次性请求凭据。图片由受控文件副本或本地传输通道交接，避免把大型图片 Base64、私密数据或任意命令塞进 URL。

下面仅为待实现的协议草案。`capture-tool` 是名称占位，不是已经注册的协议；新应用定名后确定正式 scheme。

```text
capture-tool://edit-image?v=1&ticket=<一次性交接凭据>
clip-win://capture-result?v=1&ticket=<对应结果凭据>
```

交接清单建议包含请求 ID、动作、协议版本、创建及到期时间、素材类型、尺寸、长度、内容哈希和所选结果交付方式。允许的动作、参数、素材路径与资源上限均显式校验；不接受任意网络回调或命令执行。

唤起凭据在请求被接收后即消费；编辑会话的保留期单独管理，不能因为唤起凭据过期就中断正在进行的编辑。并发请求各有独立凭据和结果，重复回调不重复写入。

当前 Clip 已有外部协议 [clip-win](D:/Repositories/Clip/src/main/integrations.ts:5)，[现有解析器](D:/Repositories/Clip/src/shared/text-tools.ts:54) 仅支持 open、search、add、copy 及相应文本参数，**尚不支持上述图片结果动作**。应用内部的 `clip://app/...` 资源协议与外部互通协议分开，不作为跨应用编辑入口。

### 3.4 结果与失败处理

| 情况 | 目标行为 |
| --- | --- |
| 工具未安装或协议不可用 | 告知原因，可选择程序或打开安装说明；不循环启动，不误报已经打开编辑器 |
| 新应用正在编辑另一张图 | 建立新的明确会话或排队，不覆盖当前未保存内容 |
| 用户取消 | 保留原记录，不回传成功结果，不改写剪贴板 |
| 用户选择复制 | 写入系统剪贴板，由 Clip 正常捕获，不再自动通过回传重复入库 |
| 用户选择回传 Clip | 使用对应请求交付结果，默认新增记录；不同时隐式复制导致重复记录 |
| Clip 已退出或历史锁定 | 新应用保留结果供保存；不自动解锁历史，回传可延期或明确说明未完成 |
| 原记录已变更或删除 | 不覆盖其他记录，回传仍按新记录处理；关联信息仅作上下文 |
| 结果损坏、参数未知或请求重放 | 拒绝导入并说明原因，不执行额外动作 |

图片编辑互通纳入迁移目标；它可在独立编辑器已经可用后接入，不让其阻塞新应用自身的打开、编辑和保存能力。

### 4.1 图片编辑的关键解耦

现有图片编辑服务通过历史记录 ID 读取原图，并通过 Clip 的记录校验与提交回调保存。新应用需改为拥有自己的素材会话：

1. 输入可来自刚捕获的画面、图片文件、剪贴板或主动交付的素材。
2. 标注工程、撤销重做和原图由新应用管理。
3. 输出为复制、文件、贴图或后续动作；不强制存入 Clip 历史。
4. 新应用的保存、放弃、锁定和恢复逻辑由自身控制。

## 5. 不能按文件名直接移走的依赖

### 5.1 SourceHost 同时承担其他桌面能力

当前 [SourceHost.cpp](D:/Repositories/Clip/native/SourceHost.cpp) 除录制来源预览，还被以下 Clip 功能使用：

- [应用图标提取](D:/Repositories/Clip/src/main/app-icons.ts:13)。
- [快捷面板光标定位](D:/Repositories/Clip/src/main/panel-placement.ts:14)。

不能删除整个 SourceHost 或构建步骤，否则可能重新破坏正式版图标和快捷面板定位。建议按职责抽出共享实现，并分别构建两款应用所需的原生程序；避免两款安装器互相寻找对方安装目录中的可执行文件。

### 5.2 CaptureWriter 是剪贴板写入器

[capture-writer.ts](D:/Repositories/Clip/src/main/capture-writer.ts) 和其 worker 处理大型剪贴板记录及拖拽容器导入，并访问 Clip Store 和同步记录。

它们继续属于 Clip。不能因为名称中有 capture 就随截图模块迁走。新应用输出到系统剪贴板后，由 Clip 原有写入流程负责历史记录。

### 5.3 其他共享职责

- [native.ts](D:/Repositories/Clip/src/main/native.ts) 包含多种 Windows 桌面操作，只迁移新应用需要的接口。
- 剪贴板格式读写可以复用适用底层能力，但历史数据库、分类和堆栈不进入新应用。
- 主题、语言、图标和基础控件可延续设计，需缩小资源及词条范围，不复制完整界面包。
- Clip 的图片格式读取、元数据、预览和保存能力仍可能使用图片相关依赖；依赖删除以引用审计为依据。

## 6. Clip 最终要移除和保留的内容

### 6.1 完成迁移后移除

1. “截图与录制”侧栏入口、工作台页面及嵌入录制视图。
2. 截图、录制、复杂标注与贴图服务的实例和专属窗口。
3. 专属 IPC、preload、renderer、权限会话和资源入口。
4. 相关快捷键注册及设置项；转移后不继续与新应用抢占同一组合键。
5. 与录制未保存状态有关的 Clip 退出、重启、数据迁移等拦截。
6. 仅服务于这些功能的构建入口、打包资源、依赖和测试。

### 6.2 继续保留

1. 图片及文件记录的预览、复制、粘贴、保存和剪贴板格式处理。
2. 大载荷剪贴板写入、缩略图、历史保护、备份及同步。
3. 应用图标提取、光标定位及快捷面板所需的桌面能力。
4. 既有历史中的截图、图片和录制文件记录，不批量删除或自动迁走。
5. 原有排除、暂停、加密和锁定规则。

旧截图快捷键配置可供用户迁移时参考，但两款应用不自动同时注册。既有录制文件可作为普通素材导入新应用；未保存录制不能靠复制内存状态迁移，升级前需处理保存或放弃。

## 7. 迁移步骤与每步交付

| 步骤 | 工作 | 可验收结果 |
| --- | --- | --- |
| 1. 独立工程 | 建立独立应用入口、设置目录、窗口、托盘和构建发布配置 | 不安装、不启动 Clip 也能运行 |
| 2. 基础能力迁移 | 接入现有截图、选区、录屏、录音、编辑和贴图的适用部分，替换历史与生命周期依赖 | 独立完成捕获、预览、复制、保存和贴图；迁移不等同于全部新增需求完成 |
| 3. 拆出共有桌面能力 | 分离原生来源预览与 Clip 图标／光标职责，整理小范围公共接口 | 两款应用各自打包并正常运行 |
| 4. Clip 清理 | 去掉迁出的页面、服务、IPC、资源和专属依赖，保留剪贴板底座 | Clip 核心工作正常，包内不再携带迁出的工作台 |
| 5. 双应用联动验收 | 验证剪贴板交付、图片编辑 URI 与回传、快捷键、焦点、录制中快捷面板和独立退出 | 两款应用互不依赖，也不互相打断；从 Clip 发起的图片编辑能完整交付结果 |
| 6. 新应用功能建设 | 按需求文档补完整选区、标注、长截图、声音控制、GIF、识别等 | 每项需求有独立完成记录和实际验收 |

步骤 2 验收通过后再完成 Clip 清理，避免迁移中途失去可用功能。拆分不长期保留两套同时发展的截图与录制实现。

## 8. 拆分后的验收

| 场景 | 预期 |
| --- | --- |
| 仅安装 Clip | 剪贴板工作正常，没有依赖新应用的启动错误或不可用录制页面 |
| 仅安装新应用 | 截图、编辑、贴图、录制、预览和导出可独立完成 |
| 两款应用同时运行 | 快捷键归属清楚，剪贴板交付遵守 Clip 设置，不重复弹窗 |
| 录制时退出或锁定 Clip | 新应用录制继续，Clip 历史锁定规则有效 |
| Clip 迁移数据目录 | 不访问、不移动新应用素材和草稿 |
| 新应用退出或升级 | 不影响 Clip 图标、光标定位、复制、粘贴和记录 |
| 新应用发生错误 | 遵循需求文档的素材保留与恢复要求，不依靠 Clip 挽救会话 |
| 正式安装包 | 两款应用可分别安装、更新、卸载，应用标识和用户目录不冲突 |
| 原有历史 | 截图和图片仍可查看、复制和保存，文件引用按原有规则处理 |
| 从 Clip 编辑图片 | URI 唤起编辑器，完成后复制或回传；原图不被隐式覆盖 |
| 并发／过期／重复 URI | 请求分别处理，过期拒绝、重复去重，不丢当前未保存编辑 |

应比较拆分前后的 Clip 安装包大小、启动耗时和资源占用。拆分会改变依赖与加载范围，但在构建及测量前不承诺减少多少 MB 或提升多少启动速度；两款应用同时运行的总资源占用也需单独记录。

## 9. 工程决策边界

独立应用方向已经明确。产品名称、独立仓库位置、首版技术栈、安装包形式与版本规则尚未确定，不影响当前功能归属和依赖梳理。

后续可基于现有代码验证独立工程。原生捕获、声音与编码方案按需求和实测结果选择，不以更换全部技术栈作为拆分前提。

OCR、识别模型和较大编码组件仍按需求文档采用按需获取建议，避免将 Clip 的臃肿问题转移成新应用的大安装包。
