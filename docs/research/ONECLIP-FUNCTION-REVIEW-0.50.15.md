# OneClip 功能借鉴与 Clipper 优化调研（0.50.15）

调研日期：2026-10-05。本文记录 OneClip 的可借鉴能力，以及 Clipper 的实施和验收范围。

> **状态更正（2026-10-05）**：此前“除媒体体验外均已实现”的结论过宽。本文保留原始调研与设计记录；当前明确缺口、暂缓事项和不跟进事项，以 [未实现功能清单](./ONECLIP-REMAINING-FEATURES-0.50.15.md) 为准。

## 实施状态（2026-10-05）

主窗口的类型、来源应用与高级筛选器共用一套临时查询状态；可组合内容类型、来源、日期、收藏、置顶、标签、文件扩展名和大小，并将已选条件显示为可单独移除的标签。搜索、收藏页、堆栈、拖拽容器及动态分类都会在这套临时条件上继续筛选。

分类编辑器已按“自动归类规则”重排为更易读的规则卡片，并扩展到类型、内容、来源、标签、创建时间、收藏、置顶、文件扩展名和大小；已填写的规则仍统一按“全部满足”处理。主窗口、后台搜索和备份导入共用匹配逻辑，避免不同入口出现不一致结果。

手动分类也已可用：新建分类时可选择“自动归类”或“手动整理”。手动分类只保存用户明确加入的记录，支持单条与批量整理；删除分类会清理其归属，备份导入会重建并映射归属关系。

分类规则在后台搜索中会先编译为单一匹配谓词；记录遍历只读取搜索与规则需要的轻量字段。这使长历史库不再为每条记录重复规范化日期、状态、扩展名和大小条件，同时保证搜索结果与主窗口分类页使用相同判断。

## 驻留内存观察（2026-10-05，本机开发态）

同一台 Windows 机器上采样到的进程结构如下，数据仅用于寻找优化方向，不能当作发布版内存指标：

| 应用 | 进程结构 | 工作集总计 | 结论 |
| --- | --- | ---: | --- |
| Clipper 已安装版 | 主进程、一个渲染进程、GPU、网络服务 | 约 226.6 MiB | 进程数已经较克制；应优先减少长文本和附件任务的瞬时分配。 |
| One 本地开发版 | 主进程、三个渲染进程、GPU、网络服务、Index/Search/Levels/Windows 原生服务 | 约 509 MiB | 多窗口与常驻索引服务是主要差异，不能直接作为 Clipper 的目标基线。 |

Clipper 后续遵循三条约束：主界面只保留摘要而不读取附件原文；高峰值任务继续在可退出的 worker 或原生辅助进程中执行；隐藏窗口和预览资源在失焦或切换后主动释放。新增分类搜索已遵循第一、二条：主线程不做全库规则遍历，worker 仅投影规则需要的字段并复用预编译谓词。

分类管理现可用明确的上移、下移操作调整顺序，保存后侧边栏和最近记录会共用该顺序；它提供了键盘可达的排序方式，后续若增加拖拽排序也必须复用同一个保存接口。设置中的存储卡同时展示容量阈值、可调整上限，以及按记录类型和来源应用汇总的内容占用估算，帮助用户在清理前判断空间去向。

## Clipper 已有基础

以下能力已经存在，不应为了追随 OneClip 再做一套平行实现：

| 能力 | 当前基础 |
| --- | --- |
| 搜索 | 全文搜索、防抖、搜索历史和结果关键词高亮 |
| 基础筛选 | 记录类型筛选、来源应用分段筛选、收藏页、分类页 |
| 来源应用 | 来源应用图标缓存、应用排除、来源筛选 |
| 分类 | 基于类型、内容、来源应用、标签的动态分类规则 |
| 批量处理 | 批量收藏、入堆栈、加入拖放容器、打标签、删除 |
| 容量控制 | 条数、保留天数和本地历史容量上限；容量可设为 64–1024 MiB |
| 文件与格式 | 文件、目录、附件、富文本、图片和可持久化原始格式保存与回贴 |
| 拖放容器 | 简洁与展开两种布局、顶部中央呼出、拖动自动显示设置 |

这些能力已组合为统一的查询与整理工作流；后续维护应继续复用同一套状态、匹配逻辑和组件，避免重新分叉。

## 已实现：统一高级筛选

### 目标

在“全部记录”搜索栏右侧提供一个筛选入口。弹层只承担编辑条件；已选条件回到搜索栏下方显示为可单独移除的条件标签。搜索文本、侧边栏页面、类型、来源应用和高级条件必须使用同一个查询状态。

### 已支持的筛选条件

1. 内容类型：文本、链接、代码、图片、文件，可多选。
2. 来源应用：多选、按名称搜索、显示图标与结果数量。
3. 日期：今天、昨天、本周、本月、自定义起止时间。
4. 状态：收藏、置顶、含标签。
5. 文件派生条件：扩展名、大小区间；仅在文件记录存在时显示。

### 交互约束

- 每个条件以一个标签展示，可单独删除；提供“清除全部”。
- 选择条件后列表立即更新，但输入文字仍保留现有防抖。
- 分类页可以复用筛选器，但分类自身规则始终先执行，临时筛选在其后叠加。
- 条件在当前窗口会话中保留；不把临时筛选意外写成永久分类。
- 查询应尽可能由 SQLite 完成。日期、类型、来源和收藏/置顶可以索引；文件扩展名和大小需要先定义可索引的摘要字段，不能为每次筛选解析附件正文。

## 已实现：规则分类编辑器

分类支持“类型、内容包含、来源包含、标签等于”及扩展规则；已填写条件统一按 AND 关系匹配，保证规则结果可预测。

分类采用两种明确模式：

- **动态分类**：由规则实时计算，不改写历史记录。
- **手动分类**：用户显式归入的分类，适合项目、客户、临时整理；它应是独立元数据，而不是伪装成标签或规则。

规则编辑器采用“先选择规则类型，再填写参数”的逐步交互，可支持：

- 内容包含指定文本；
- 来源于指定应用；
- 内容类型；
- 创建时间范围；
- 已收藏、已置顶、包含某标签；
- 文件扩展名、文件大小；
- 是否含富文本、图片、附件。

第一版规则之间只支持“全部满足”，界面应明确写出。只有确认真实需求后，再增加“任一满足”或规则组；否则规则解释、索引和边界都会明显复杂化。

“永久保存”不能只是分类开关。若启用，它应明确代表“匹配的记录不参与自动清理”，并显示受保护条数和占用空间；容量满时仍需要让用户有可理解的处理路径。子分类也应晚于手动/动态分类模型稳定后再做。

## 已实现：从检索走向整理

### 搜索上下文

搜索结果的操作菜单增加“在时间线中显示”。执行后清除文本搜索或切换为定位模式，跳转到该记录所在位置并保持选中。这样用户能看到复制前后发生了什么，而不需要自己重新搜索。

### 批量拖拽

批量选择已覆盖收藏、堆栈、容器、标签、分类与删除，并已完成 Windows Shell 的真实目标兼容性处理；后续修改应保持批量文件操作与单文件拖动使用同一数据边界。

### 分类排序

分类导航可以支持显式排序，默认按创建顺序或名称。拖拽排序必须保存稳定排序字段，并有键盘等价操作；系统入口、收藏、堆栈等固定导航不与自定义分类混排。

## 存储管理原设计（分类保护待补）

本地历史上限可调整，默认值为 256 MiB。以下是存储页和满容量反馈的原设计要求；手动分类保护尚未实现，实际行为以[未实现功能清单](./ONECLIP-REMAINING-FEATURES-0.50.15.md)为准：

- 展示按记录类型、来源应用、时间段统计的占用；
- 在约 80% 和 90% 容量时给出非打断提醒，在满容量时提供“管理空间”和“调整上限”；
- 清理前展示预计释放空间，并保留收藏、置顶、堆栈、容器、共享和手动分类保护项；
- 对“永久保存”或高容量文件记录显示容量影响，避免用户在无感知的情况下让自动清理失效。

## 文件类型的演进方式

Clipper 当前的主类型保持为文本、链接、代码、图片、文件更合适：它与原始格式保存、附件和粘贴路径已经稳定。不要为了对齐 OneClip 把 `files` 直接拆成视频、音频、文档、压缩包和应用程序。

更稳妥的做法是在文件记录上派生“文件特征”：PDF、Office、压缩包、音频、视频、安装程序、脚本等。这些特征可以用于筛选、徽标和空间统计，同时不改变记录的保存和回贴模型。

## 明确暂不跟进

- 独立快速粘贴面板：已由用户决定移除，不能重新引入与“最近记录”重复的入口。
- 划词菜单 / PopClip：已按用户要求全面移除。
- 截图、录屏、录音的进一步优化：当前按用户要求暂缓。
- macOS Dock、刘海屏/灵动岛触发、Touch ID 等平台特性：不直接迁移到 Windows。
- 插件系统：OneClip 当前也仅列为 TODO；不在本轮范围内。
