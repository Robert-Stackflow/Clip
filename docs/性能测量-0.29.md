# 0.29 响应测量

目的：确认界面重排没有引入选取时全列表重建，建立后续持续优化基线。

测试使用相同无头 Chromium、1240×780 视口、10000 条合成记录，收藏位于列表末尾；每轮连续选取 60 次，共三轮。比较冻结的 0.28 与本次构建。

| 测量 | 0.28 | 0.29 |
| --- | --- | --- |
| 事件处理时间中位数的三轮平均 | 0.40 ms | 0.43 ms |
| P95 的三轮平均 | 1.23 ms | 0.80 ms |
| 被重建的列表行 | 0 | 0 |
| 当前列表行数 | 100 | 100 |

样本量较小且存在测量波动。这只测量选取事件处理，不能推断整体快了多少，也不包含绘制、真实剪贴板捕获、数据库或大文件任务。详细样本保存在交付源码 validation/performance.json。

运行中的 One 与 Clipper 已做只读进程工作集观测，未切换或关闭它们。窗口状态、任务和运行时间未控制；共享内存会重复计数，因此该观测仅用来确定后续测量方法，不作为优劣结论。原始范围说明见 validation/memory-observation.json。

接下来测量：相同后台/前台状态下的稳定私有内存和峰值；长文本搜索与编辑；大文件快照、同步、导出及取消；持续追踪任务的耗时和回收。优先减少副本、批量处理与主线程工作，在证据表明有收益时引入 Rust。
