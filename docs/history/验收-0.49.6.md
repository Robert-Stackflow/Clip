# 0.49.6 同时间长文本的排序索引

0.49.5 加密资料的追加阶段采样中，最近记录界面在 8 秒闲置后退出，主进程 JavaScript 堆约 9 MiB，关闭后总工作集回到打开前附近，没有复现前次高驻留。诊断报告为 work/current/recent-search-memory-2-current/result.json；不能据此解释或排除前次的高驻留。

进一步检查实际搜索执行计划，发现当前索引仅含更新时间，而最近记录按更新时间和记录 ID 排序。同一时间的多条长正文进入临时排序。新增 clips_recent_order(updated DESC,id ASC) 可重建索引，执行计划使用覆盖索引并取消临时排序；原有索引保留。解释执行计划的方法参考 [SQLite 官方文档](https://sqlite.org/eqp.html)，程序不解析或依赖执行计划文本。

首次完整回归发现该索引改变了普通列表同时间记录的遍历顺序。普通列表、完整导出与主窗口搜索明确保留原有 rowid 插入顺序；最近记录保留原有 ID 顺序。保留规则的旧断言未放宽，新增验证独立核对 93 条同时间记录升级前后的普通列表与完整原记录、只读检查不修改数据库、重复打开、工作线程搜索、精确总数及前 80 条身份。数据库版本仍为 7，主记录、触发器和备份格式不变。

## 独立进程对照

同一份生成资料复制两份，只改变排序索引，四种组合（明文/加密、不同时间/同时间）各三轮、每版新进程读取，合计 24 个样本。每份含 1,500 条约 7,400 万字符的长文本。前 80 条身份使用独立 SQL 验证，原正文不进入返回结果；候选执行计划均没有临时排序。

| 场景 | 搜索时间旧版→新版（中位数） | 读取进程峰值工作集旧版→新版 |
| --- | --- | --- |
| 明文，不同时间 | 312.8→299.3 ms | 85.1→84.9 MiB |
| 明文，同时间 | 593.0→305.4 ms | 89.2→84.9 MiB |
| 加密，不同时间 | 495.0→482.4 ms | 101.3→101.1 MiB |
| 加密，同时间 | 509.0→495.8 ms | 160.0→101.0 MiB |

加密同时间查询本身的峰值增量为 98.9→39.8 MiB。此处是独立 Node 读取进程，不是 Electron 整个程序的峰值；未强制 GC 或调整工作集。升级使生成数据库增加 81,920 字节；包含数据库打开、现有索引检查、新索引建立和关闭的总时间为 271–579 ms，不能全部归为新索引创建耗时。报告为 work/current/recent-search-order-profile/result.json。

## 发布程序对照与待收尾项

499 项核心回归、类型与语言检查通过。0.49.6 目录包已生成；原生程序对照有 15 个完整有效样本：两版各五轮明文，旧版三轮加密、新版两轮加密。默认 80 条身份、完整 Unicode 查询与精确计数、收藏和文件分类、原图片与附件、取消、重开和加密锁定均通过这些样本的检查。

明文搜索等待中位数为 1,143→1,023 ms，范围为旧版 1,108–1,354 ms、新版 1,012–1,533 ms。全应用峰值增量中位数为 198.9→189.3 MiB，但新版最高一轮仍为 241.2 MiB，不能声称已经稳定降低整体峰值。加密样本尚未配齐：旧版搜索为 1,173–1,361 ms，新版已有两轮为 1,361–1,383 ms，新版锁定界面为 379–398 ms。独立读取进程的内存收益不能等同于整个应用更快；当前数据存在加密等待变长的迹象，应保留为待解决问题。

旧版加密第三轮关闭 10 秒后隐藏窗口仍存在，新增工作集为 135.6 MiB；这是完整有效样本，保留在报告中，原因尚未确定。新版加密第三轮窗口焦点检查失败，没有产生完整有效报告。最终诊断确认测试窗口有 Electron 焦点，但 Windows 前台属于其他进程；测试已移除物理鼠标点击，仍严格验证自身窗口的真实前台身份，未向其他窗口输入。该轮不能计为通过，也不能用重跑覆盖旧版已完成的异常样本。原始报告为 work/current/recent-search-order-plain-0…4，以及 recent-search-order-encrypted-0…2-baseline 和 recent-search-order-encrypted-0…1-current；失败日志为 work/recent-order-encrypted-2-current.log。完整 16 样本汇总尚未通过，不再反复重跑已通过的轮次。
