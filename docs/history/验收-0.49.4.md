# 0.49.4 最近记录搜索等待

在 0.49.3 的后台只读搜索基础上减少重复解析和文本复制。已有预览索引的记录只解析一次文字及文件名投影；先检查类型、收藏、来源和标签条件，再进行正文匹配。正文只做一次大小写转换，搜索词分别在正文和来源/标签中匹配，保留完整正文、准确计数、最近 80 项和同时间记录的排序。

预览索引不含 PNG、附件原字节、HTML 或 RTF 正文。旧数据库继续通过 SQL 提取所需文字与文件名，不把原二进制内容传入 JavaScript。没有更改加密格式、密钥派生、完整性检查或线程取消/退休规则；也没有新增常驻查询线程或正文缓存。本轮不修改已验收的资料页间距，不调查录音录屏性能。

495 项核心检查、TypeScript 与语言覆盖检查通过。新增独立完整记录参考结果，覆盖明文/加密及有索引/旧数据库四种组合；检查 Unicode 大小写、多个搜索词、完整字段边界、自定义分类、收藏、类型、精确总数、同更新时间排序、80 项上限和原附件保持。在 SQLite 返回的行进入读取器时检查原图片、附件、缩略图和富文本正文没有传出，避免只比较工作线程与其调用的同一个读取器。

算法对照以提交 f4b18f0 的 0.49.3 查询为固定基线。两版在相同生成资料上交替执行五轮，每次新开只读连接，共 1,500 条记录、73,758,390 个正文字元。数据库仍在磁盘上，完整结果为 1,500，返回最近 80 项。测量包含 SQL 取行及匹配，不包含工作线程启动、输入等待或界面显示，不能作为操作总延迟。

实际发布包 0.49.3 与 0.49.4 各五轮明文、各三轮加密历史对照。每次启动独立进程，使用相同构成的隔离资料：1,500 条长正文、一份附件、一张图片和一个自定义文件分类；两版交替顺序，测试自己的窗口使用实际 Windows 输入取得焦点，随后恢复鼠标位置和置顶状态。加密轮次通过实际界面 API 启用历史加密，并核对磁盘文件不是明文 SQLite。

搜索等待从输入搜索框开始，包含 180 ms 输入等待、线程启动、读取与匹配、线程退出和计数显示。本轮持续观察界面帧上的计数和加载状态，减少断言重试间隔对计时的影响；两版都采用同一测法。因此只比较下面这轮配对数据，不将 0.49.3 上一轮的 938 ms 明文或 4,072 ms 单轮加密读数与它直接比较。主窗口请求仍包含自动化通信，5 ms 计时器在 Windows 上通常约 16 ms 执行一次；这些指标不能等同真实硬件输入延迟。

明文操作总等待减少约 7.2%，加密减少约 13.5%。算法扫描时间减少得更多，实际总等待还包括线程、界面和输入等待，不能把算法改善比例当成完整操作改善。加密锁定检查均关闭最近记录窗口，新版范围为 311–424 ms；旧版为 283–320 ms，本轮没有改善锁定耗时。

默认 80 项、全文与 Unicode/标签联合搜索总数 1,500、收藏总数 500、自定义文件分类一项及预览、搜索中关闭/重新打开恢复默认条件均通过；原 PNG 和附件字节保持。一次明文第 1 轮在初始化时前台切回 Codex，最近记录按产品失焦规则关闭，计数被清空。这次失败日志保留在 work/recent-search-wait-plain-1.log，不计入结果；同一轮重新聚焦后通过，未关闭软件的失焦保护或修改产品行为。

工作集按本次程序进程树每 250 ms 采样，没有强制 GC。明文新版峰值增量为 170.9–233.1 MiB，旧版为 205.4–212.6 MiB；新版有一轮更高。加密新版峰值和关闭后驻留的中位数也略高，不能将本轮称为整体内存优化，应用总峰值和长期驻留仍待处理。

操作报告为 work/current/recent-search-wait-plain-0 至 -4、recent-search-wait-encrypted-0 至 -2 下分别带 -baseline/-current 的报告与截图；汇总为 work/current/recent-search-wait-summary/result.json。0.49.4 的 263 项发布构建文件一致性核对通过，保留 0.49.4 与 0.49.3。开发监听正常重启并显示已就绪，本轮已完成的界面间距没有改动。整体性能、峰值和长期驻留任务保持未完成。
